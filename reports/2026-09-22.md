## 追記: フォローアップサイクル（2026-09-22、同日実施）

本体サイクルで「未完了」とされていた項目のうち、永続化・Docker検証・
認証の3点に着手した。ドメイン取得・決済連携・本番デプロイ等、引き続き
人間の承認が必要な項目には一切着手していない（従来通りの制約は継続）。

### 実装内容

1. **永続化の実装（最優先課題を解消）**
   - `server/persistence.js` を新設し、ローカルディスク上のJSONファイル
     （デフォルト `data/pulseboard.json`）へ、一時ファイル＋rename方式の
     アトミック書き込みで状態を保存する方式を実装。外部DB・クラウド
     サービスへの依存は一切なし。
   - `server/store.js` に `persistPath` オプションを追加し、指定時は
     監視対象・チェック履歴・インシデント・プラン設定を書き込みの都度
     永続化、起動時に読み込む。`persistPath` 未指定時は従来通りの
     純インメモリ動作を維持（既存テストへの影響なし）。
   - `server/index.js` で `DATA_FILE` / `PERSIST=0` 環境変数により
     設定可能にし、既に永続化データが存在する場合はデモ監視対象の
     再シードをスキップするようにした。デモターゲットサーバーの
     ポートも永続化有効時は固定化し、再起動をまたいでデモ監視対象の
     URLが有効なままになるようにした。
   - `tests/persistence.test.js`（12件）を新規追加。ファイルの
     読み書き・破損ファイルへの耐性に加え、「2つ目の独立した
     `createStore()` インスタンスが同じファイルから状態を復元できるか」
     という形で**サーバー再起動を模した検証**を実施。
   - **実プロセスでの動作確認も実施**: サーバーを起動→APIで監視対象を
     1件作成→プロセスを`kill -9`→同じデータファイルを指す新規
     プロセスを起動→`GET /api/monitors`で作成した監視対象とその
     チェック履歴が復元されていることを確認した（単体テストだけでなく
     実際のプロセス再起動で検証済み）。

2. **Dockerfileの検証**
   - 本サイクルでも引き続きDockerデーモンが本環境で利用不可
     （`docker build`/`docker info`がソケットに接続できず、
     `dockerd`の起動はsandboxの`ulimit`制限によりブロックされる）ため、
     実際の`docker build`は実施できなかった。
   - 代替として: `COPY`対象パスが実際のリポジトリ構成と一致することを
     確認、Dockerfile内の`npm ci --omit=dev`をリポジトリの隔離コピーで
     実際に実行し成功を確認（express本体は入り、devDependencyの
     supertestは除外されることを確認）、さらに同じ隔離環境で
     `NODE_ENV=production`でサーバーを起動し、Dockerfile内の
     `HEALTHCHECK`コマンドと全く同じコマンドを実行してHTTP 200 /
     exit 0 を確認した。目視・手動検証で不具合は見つからなかった。
   - 永続化データが`/app/data`に書き込まれるようになったため、
     `VOLUME ["/app/data"]`をDockerfileに追加（コンテナ再作成をまたいで
     データを残すには、人間がボリュームをマウントする必要がある旨を
     コメントで明記）。

3. **追加機能: 管理ダッシュボードの任意Basic認証**
   - QA_NOTES.mdの既知の制約その2（認証なし問題）に対応。
     `ADMIN_USER` / `ADMIN_PASSWORD` の両方を設定した場合のみ、管理
     ダッシュボード（`/`）と管理系APIルート全て（監視対象の追加・削除・
     手動チェック・プラン変更）にHTTP Basic認証を要求する。両方とも
     未設定の場合は従来通り無認証（ゼロコンフィグのローカルデモ動作を
     維持）。公開ステータスページ（`/status.html`、`GET /api/status`）は
     認証設定の有無にかかわらず常に無認証のままとした。
   - `tests/auth.test.js`（8件）を新規追加。加えて実プロセスに対して
     `curl`で認証なし/誤った認証情報で401、正しい認証情報で200、
     公開ステータス系は常に200になることを確認した。

機能（サインアップ・ログイン・メールアドレス収集）は、今回もオーナー
の指示により意図的に対象外とした**（後述）。

### 実装内容

1. **Webhook通知機能（新規）**
   - 監視対象ごとに任意のWebhook URLを設定可能にした
     （`server/notifier.js`）。up→down、down→upの実際の状態遷移が
     発生した時のみ（初回チェック時は「直前の状態」が存在しないため
     送信しない）、監視対象名・URL・新しいステータス・直前の
     ステータス・タイムスタンプを含む小さなJSONをそのURLへPOSTする。
   - 外部の有料サービスやAPIキーは一切不要。Slack/DiscordのIncoming
     Webhook URLをそのまま貼り付けても動作するし、任意の自前
     エンドポイントでも良い。
   - 配信失敗（タイムアウト・接続拒否・非2xx応答）は**必ずログに
     記録した上で握りつぶし**、チェックループを止めない設計にした
     （`checkMonitorAndNotify`内で二重に例外を捕捉）。
   - `tests/webhook.test.js`（8件）でローカルHTTPサーバーを「Webhook
     受信サーバー」役として使い検証。実際の外部URLには一切アクセス
     していない。

2. **稼働率の長期集計（新規）**
   - 既存の「直近50回チェックのローリング稼働率」に加えて、日別の
     up/downタリー（最大90日分、それ以降は自動的に間引き）と
     全期間の累計カウンタを`server/store.js`に追加し、
     `uptimeStats`として `last24h` / `last7d` / `last30d` / `allTime`
     の稼働率を算出できるようにした。
   - 無制限にチェック履歴を溜め込むのではなく、日単位の小さな
     集計値のみを保持する設計とし、サイズを有界に保った
     （`tests/uptimeStats.test.js`で90日超の間引きも検証済み）。
   - `GET /api/monitors` と `GET /api/status` の両方に追加し、
     管理ダッシュボードと公開ステータスページの両方に表示した。
   - `last24h`はUTC暦日単位の集計であり厳密な「直近24時間」の
     ローリングウィンドウではない点をREADME.mdに明記した
     （過度に精度を誇張しないため）。

3. **監視対象ごとのチェック間隔カスタマイズ（新規）**
   - 監視対象ごとに任意の`intervalMs`を設定でき、全体設定
     （`CHECK_INTERVAL_MS`）を上書きできるようにした。5秒〜24時間の
     範囲でバリデーションし、対象を過度な高頻度でハンマリングしない
     よう制限した。
   - 既存の監視対象を編集できる `PATCH /api/monitors/:id` を新設。
   - スケジューラは全体間隔より短い間隔でtickし、監視対象ごとの
     `intervalMs`が実際に守られるようにした（`checkDueMonitors`、
     `tests/monitorInterval.test.js`で検証）。

4. **APIレート制限（新規）**
   - `/api/*` 全ルート（公開の`/api/status`含む）に、インメモリ・
     IPアドレス単位の固定ウィンドウ方式のレート制限を追加した
     （デフォルト: IPあたり60秒間に120リクエスト、
     `RATE_LIMIT_MAX`/`RATE_LIMIT_WINDOW_MS`で変更可）。
   - 超過時は`429`と`Retry-After`ヘッダーを返す。プロセス単体の
     インメモリ実装であり、複数インスタンス間では共有されない点を
     制約として明記した。
   - `tests/rateLimit.test.js`（6件）で検証。各アプリインスタンスが
     独立したカウンタを持つため、テスト間の干渉もない設計にした。

5. **実ブラウザによるUIスモークテスト（新規）**
   - `playwright`（1.63.0）をdevDependencyとして追加し、
     `scripts/ui-smoke.js`を新設（`npm run smoke:ui`で実行、
     `npm test`本体には含めない）。
   - 本環境に事前インストールされたヘッドレスChromium
     （`PLAYWRIGHT_BROWSERS_PATH=/opt/pw-browsers`）を実際に起動し、
     一時データファイルを使ったサーバーに対して: ダッシュボードを
     開く→実際のHTMLフォームに監視対象名・URLを入力して送信→
     カードが表示されることを確認→「今すぐ確認」ボタンを実際に
     クリックして本物の「稼働中」ステータスになることを確認→
     公開ステータスページを開いて同じ監視対象が表示されることを
     確認、という一連の操作を実際のブラウザで行った。
   - `screenshots/dashboard.png` と `screenshots/status.png` に
     スクリーンショットを保存し、`QA_NOTES.md`から参照する形で
     「実際に動いた証拠」として残した。これは前サイクルの
     QA_NOTES.mdが指摘していた「実ブラウザが本環境になく手動での
     目視確認のみ」というギャップを解消するものである。

6. **Dockerビルドの再挑戦**
   - 今回は`dockerd`の起動自体には成功した（前サイクルまでの
     「デーモンに接続できない」状態から改善）。しかし
     `docker build -t pulseboard 2026-09-22-pulseboard`を実行した
     ところ、ベースイメージ`node:20-alpine`の取得段階で失敗した。
     本環境のプロキシ診断機能で確認したところ、これは
     `production.cloudfront.docker.com`（Docker Hubの配信CDN）への
     アクセスが本サンドボックスのネットワークポリシーにより
     `403 Forbidden`で明示的に拒否されているためであり、一時的な

     従い、ポリシーによる明示的な拒否は迂回・再試行せず、事実を

### 未完了・引き続き人間の判断が必要な事項

- **マルチユーザーアカウント機能（サインアップ・ログイン・メール
  アドレス収集）は、今回のサイクルでも意図的に対象外とした。**
  これは実装漏れではなく、オーナーの明示的な指示による意図的な
  先送りである。理由: (1) 本格的なアカウント機能は認証方式の選定・
  セッション管理・データモデルの再設計を伴う大きめのアーキテク
  チャ判断であり、今回の他の改善項目（Webhook・長期集計・間隔設定・
  レート制限・UI検証・Docker検証）と同時に安全に実装できる規模では
  ないと判断したこと、(2) メールアドレス等の個人情報を初めて収集する
  機能となるため、`LEGAL_REVIEW.md`が既に指摘している通りプライバシー
  ポリシーの正式な作成が同時に必要になり、これは人間が内容を最終
  確認すべき法務判断であること。したがって、マルチユーザー機能は
  「忘れられた」のではなく、上記の理由により次回以降のサイクルに
  明確に先送りされたものである。
- Dockerイメージの実ビルド確認は、本環境のネットワークポリシーに
  よりDocker Hubへのアクセスが拒否されるため、依然として未達成。
  Docker Hubへの通常のアクセスが可能な環境で人間が一度
  `docker build`/`docker run`を実行して最終確認することを推奨する。
- レート制限はプロセス単体のインメモリ実装であり、将来的に複数
  インスタンスを並べて運用する場合は共有ストア（Redis等）への
  移行を検討する必要がある。
- 実際の決済連携（Stripe等）、ドメイン取得・DNS設定、実デプロイは、
  これまで通り人間の判断・実行が必要な領域であり、本パイプラインは
  一切手を付けていない。
